The daemon's cross-agent contract: the SQLite schema, the event-kind
vocabulary, and the socket protocol. **Frozen.** Tickets 012, 013 and 014 all
read this. Adding a `kind` or a field inside `data` is additive and fine;
changing a column, a kind's name, or the meaning of an existing field is not,
and needs a superseding record.

## Two stores, and only one of them is state

Ticket files under `.project/tickets/` are the source of truth for *what a
ticket is*. `events.db` is a record of *what happened*. Deleting the database
must lose history and never state — that is why the project registry is a text
file and not a table, why there is no pruning, and why `rm events.db` is the
supported reset. `tests/test_daemon.py::test_deleting_the_event_db_leaves_every_ticket_stage_intact`
is the check.

## Schema — `~/.local/state/pipeline/events.db`

Opened `journal_mode=WAL` (so a reader never blocks the daemon's `emit`),
`synchronous=NORMAL`, `busy_timeout=5000`, `PRAGMA user_version=1`.

```sql
CREATE TABLE IF NOT EXISTS events (
  id      INTEGER PRIMARY KEY,          -- rowid; monotonic, doubles as the subscribe cursor
  ts      REAL NOT NULL,
  project TEXT NOT NULL,                -- absolute path as registered; "" for daemon-level events
  ticket  TEXT,                         -- NULL for daemon-level events
  stage   TEXT,
  session TEXT,
  kind    TEXT NOT NULL,
  data    TEXT NOT NULL DEFAULT '{}'    -- JSON, kind-specific
);
CREATE INDEX IF NOT EXISTS events_proj_ts ON events(project, ts);
CREATE INDEX IF NOT EXISTS events_ticket  ON events(ticket, id);
CREATE INDEX IF NOT EXISTS events_kind_ts ON events(kind, ts);

CREATE TRIGGER IF NOT EXISTS events_no_update BEFORE UPDATE ON events
  BEGIN SELECT RAISE(ABORT, 'events is append-only'); END;
CREATE TRIGGER IF NOT EXISTS events_no_delete BEFORE DELETE ON events
  BEGIN SELECT RAISE(ABORT, 'events is append-only'); END;
```

Append-only is a trigger, not a comment: four lines, and `UPDATE`/`DELETE`
raise `sqlite3.IntegrityError: events is append-only` from any connection,
including a `sqlite3` shell.

`Store.emit()` is the only writer:

```python
store.emit(project, kind, ticket=None, stage=None, session=None, **data) -> dict
store.emitter(project)          # emit with the project bound: emit(kind, **kw)
store.cursor() -> int           # MAX(id)
store.since(cursor, project=None, ticket=None, limit=1000) -> list[dict]
store.listeners: list           # live fan-out; the Server appends one callback
```

`emit()` returns the committed row as a dict with `data` already decoded — the
same shape `since()` returns and the same shape the socket sends.

## Event kinds — frozen vocabulary

| kind | emitted by | data |
|---|---|---|
| `stage_start` | `spawn()` / `spawn_command()` | `{model, mode, pid, log, wt}` |
| `stage_end` | `finish()` | `{result, next_stage, exit_code}` |
| `transition` | `advance()` | `{from, to, result, counters}` |
| `escalated` | `escalate()` | `{reason}` |
| `gate` | `gate()` call sites | `{verdict, findings:[...]}` |
| `init` | 012 | `{model, tools, permission_mode, capabilities, ...}` |
| `assistant` / `tool_use` / `tool_result` | 012 | stream-json passthrough |
| `hook_started` / `hook_response` | 012 | `{hook, exit_code, outcome, stderr}` |
| `result` | 012 | `{total_cost_usd, num_turns, duration_ms, usage, modelUsage, ...}` |
| `rate_limit` | 012 | passthrough |
| `usage` | `finish()`, interactive stages only | `{model, input_tokens, output_tokens, cache_read, cache_creation}` |
| `daemon_start` / `daemon_stop` | 011 | `{pid, version}` |

TICKET-011 emits only the first five plus `daemon_start`/`daemon_stop`.

Where 012's kinds actually reach the store: `supervisor.event_sink()`, bound to
`rec["sink"]` in `spawn()`. A kind the parser produces that is not in the table
above (`other` -- a truncated or unknown line) is dropped rather than stored.
`transition` has a second emit site: `cmd_approve`/`cmd_reject`/`cmd_answer`
open the store directly, because a human gate is left in the CLI's process and
not the daemon's, and the parked-time view closes its span on that event.
`escalated` has one too -- `advance()`, when `transition()` returns `escalated`
because a loop bound was charged. `escalate()` never routes through `advance()`,
so the two cannot double-emit for one ticket.

`mode` on `stage_start` is `"batch"` for an agent, or the child's `kind`
(`suite`, `merge`, `regate`) for a dispatcher-owned script. TICKET-013 adds
`"interactive"`; the same value appears on `ls` rows.

`stage_end.result` is the agent's claimed result on the happy path, and
otherwise names the reason the stage did not produce one: `tampered`,
`wrote-in-readonly`, `no-result`, `bad-claim`, `escalated`.

## Socket protocol — `$XDG_RUNTIME_DIR/pipeline/daemon.sock`

NDJSON, one object per line, both directions. **Five ops:**
`ping`, `ls`, `projects`, `subscribe`, `kill`.

```json
-> {"id":1,"op":"ls","project":"/home/u/proj"}
<- {"id":1,"ok":true,"data":[{"project":"...","id":"TICKET-003","stage":"planning",
                              "class":"refactor","counters":{},"lease":{},
                              "running":true,"mode":"batch","title":"..."}]}
<- {"id":1,"ok":false,"error":"project not registered"}

-> {"id":2,"op":"subscribe","project":"...","since":12034}
<- {"id":2,"ok":true,"data":{"cursor":12040}}     // always first
<- {"sub":2,"event":{"id":12035,"ts":...,"kind":"transition","data":{}}}
<- {"sub":2,"dropped":57}
```

`subscribe` needs an integer `id`; it becomes the `sub` tag. The reply comes
first, then the `since` replay, then live events — one thread, so nothing
arrives twice and nothing is missed. A reconnecting client passes its last-seen
`id` and loses nothing.

`--project` is a **filter**, never a target: absent means every registered
project. Over the socket a path that is not registered is an error rather than
an empty list -- the daemon can only speak for what it watches, and a typo must
not read as "nothing is running". The CLI's file fallback is deliberately wider:
`pipeline --project X ls` reads X's ticket files whether or not X was ever
registered, and it falls back rather than erroring when the daemon refuses.

`server.ticket_rows(project, inflight=None)` builds those rows and is the
**single** implementation -- the daemon serves them and the CLI builds the same
ones from disk. `running` means "a child is in flight"; `leased` is
`Ticket.lease_active()` (never `lease["expires"]`, which survives an expiry and
is only nulled by `release_lease()`); `stale` means untouched for `STALE_HOURS`
while not leased and not sitting at a human gate.

**No `approve`/`reject`/`answer` ops, deliberately.** They mutate the ticket
file, which is the source of truth, and the next tick notices. `cmd_approve`
already refuses unless the stage is `awaiting-approval`, and that is a
`HUMAN_GATE` the dispatcher never spawns into, so there is no lease to race.
Four TUI keybindings with zero protocol surface — do not spend it.

## Trust boundary: the socket is same-uid, and that is all it is

`0700` directory, `0600` socket (`umask` around `bind()`, never `chmod` after),
`0600` event database. There is no authentication beyond the uid -- anything
running as this user can `ls`, `subscribe` or `kill`. That is the intended
boundary and it grants nothing new: a write-stage agent already has a shell as
the same user, so it could signal the same children and read the same ticket
files directly. **Do not build a feature that assumes the socket is a privilege
boundary.**

`Server._claim()` -- an `flock` on `daemon.sock.lock` -- is what makes "there is
one daemon" true. The connect probe is evidence, not a claim: two daemons
starting in the same millisecond both probe, both see `ECONNREFUSED`, and the
second would unlink the first's live socket.

Bounds: `MAX_CONNS=64` clients (accept-and-refuse past it), `MAX_SUBS=8`
subscriptions per connection, `MAX_LINE=1MiB` per request, `OUTBOX=1000` frames
per connection. `accept()` failing with EMFILE unwatches the listener rather
than spinning forever on a level-triggered readable fd.

## The select loop is the extension point

```python
server.watch(fd, callback)   # callback(fd) whenever fd is readable; re-watch replaces
server.unwatch(fd)           # idempotent, and safe on an already-closed fd
```

`Poller` is the bare loop (`pipeline run` standalone uses it); `Server` is
`Poller` plus the listening socket. Callbacks must not block — they get one
non-blocking read and return. A callback that raises is logged and the loop
continues.

`supervisor.run()` and `supervisor.serve()` both end their tick in
`poller.poll(timeout)` instead of `time.sleep()`. Registering a new fd is two
lines at the call site and touches nothing in `server.py`.

## Registry

`~/.config/pipeline/projects` — one absolute path per line, `#` comments,
re-read every tick. Per-project settings stay in `.project/pipeline.toml`.

`projects()` returns only absolute paths whose `.project/` exists -- the file is
hand-editable, and `lock()` would otherwise `mkdir -p` a `.project/` at whatever
a typo named. `register`/`unregister` rewrite it with `write_atomic`, because
the daemon re-reads it every tick and a reader that caught a truncated file
would see an empty registry and release every project it was watching.

Each watched project is claimed with `fcntl.flock(LOCK_EX | LOCK_NB)` on
`<project>/.project/.lock` for as long as it is watched. Two supervisors on one
project double-spawn — the ticket lease does not prevent it, because both see
no lease in the same second. The kernel releases a flock on crash, so there is
no stale-lockfile path to get wrong. `pipeline run` takes the same lock and
refuses to start if the daemon already holds it.
