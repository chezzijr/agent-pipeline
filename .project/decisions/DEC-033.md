# DEC-033

- ticket: none -- done by hand, dispatcher down
- branch: main
- files: pipeline/stages/triage.md
- decided: 2026-08-21

**`triage` runs on Sonnet. On a Max plan the metered unit is tokens, and Opus
draws on a weekly limit of its own.**

DEC-024 set every stage's `effort` and warned that "a later cost-cutting pass
must not flatten them". This is that pass, and it does not touch effort. It
changes the model on the one stage whose cost is not reasoning.

Measured over 20 tickets: `triage` spent 26M tokens and $33.02 to reproduce one
named failure and run one command. Its `effort: low` is already working --
thinking is 19% of its output, the lowest of any Opus stage -- so there is no
thinking to cut. The volume is 1.3M cache-read tokens per run of *context*.

77% of all pipeline tokens land in the Opus bucket. That bucket is capped
separately from every other model and is what runs out first, which is why cost
in USD was the wrong number to optimise against: Opus:Sonnet is only 1.67:1 on
price, but 1:0 on the limit that actually binds.

What this accepts: `triage` owns the `chore` verdict, which skips `planning`,
`plan-validation` **and the human approval gate**. A Sonnet triage that
over-calls `chore` routes work around the only checkpoint in the system. Two
things already stand in the way -- the prompt says "`ok` is the safe answer
whenever you are unsure", and a `quick-review` returning `fail` sends the ticket
back to `planning`. The tripwire is `quick-review` runs appearing in
`pipeline metrics`, which have been zero to date. If they appear and start
failing, this decision is what to revisit first.
